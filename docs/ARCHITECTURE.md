# Древо села — архитектура

Документ для владельца и для тех, кто меняет код (в том числе AI-агентов).
**Прежде чем менять код, прочитайте «Незыблемые правила».**

---

## Незыблемые правила

1. **Древо — главное.** Ни одно изменение не должно ставить под угрозу `data/tree/tree.db`.
   Перед любым изменением схемы контейнер сам делает копию; изменения с потерей данных
   `prisma db push` не выполняет, а останавливается.
2. **Древо и пользователи хранятся отдельно.** В базе древа нет паролей и аккаунтов;
   связь — только по id (`ChangeLog.actorId`, `accounts.json → personId`), без внешних ключей.
3. **Без входа не видно ничего**, кроме страницы входа. Каждая страница вызывает
   `pageUser / pageKeeper / pageOwner`, каждый API — `requireViewer / requireEditor /
   requireKeeper / requireOwner` (`lib/auth.ts`).
4. **Всё, что меняет древо, пишется в журнал** (`writeChangeLog`): кто (id + имя), что, когда,
   было/стало. Записи журнала не удаляются и не правятся.
5. **Удаление человека и слияние дублей — только с подтверждением** (кроме владельца).
6. Человек никогда не дублируется, чтобы попасть в два рода (см. модель данных ниже).

## Из чего состоит

```
Next.js 16 (страницы + API в одном процессе)        next start, порт 3000
├── база древа    data/tree/tree.db    SQLite через Prisma (prisma/schema.prisma)
├── пользователи  data/accounts/       accounts.json + auth-log.jsonl (lib/accounts.ts)
└── копии         backups/             tree/, accounts/, status.json (scripts/backup.mjs)
```

Два контейнера (`docker-compose.yml`) из одного образа:

| Сервис   | Что делает |
|----------|------------|
| `web`    | при запуске: копия → разделение баз → `prisma db push` → сайт |
| `backup` | `scripts/backup.mjs --loop`: древо каждые 6 ч, аккаунты раз в сутки, отправка в S3 |

Служебные скрипты (`scripts/*.mjs`) работают на Node 22 со встроенным `node:sqlite`
и **не зависят от Prisma** — чтобы бэкап и восстановление работали, даже если сайт сломан.

### Почему пользователи — файл, а не вторая база

Жителей десятки, максимум сотни; процесс сайта один. Файл с атомарной записью
(временный файл → `rename`) надёжен, читается глазами, копируется одной командой
и не требует второй СУБД. Если пользователей станет тысячи — перенести в SQLite.

## Данные древа (prisma/schema.prisma)

- `Person`, `PersonAlias` — люди и другие написания имени.
- `ParentChild`, `Marriage` — граф родства. Род (`Clan`) вычисляется по отцовской линии
  до родоначальника; заявленный род (`claimedClanId`) — только подсказка.
- `ChangeLog` — журнал: `action`, `personId`, `actorId`, `payload` (JSON: имя автора,
  было/стало, снимок удалённого).
- `ChangeRequest` — заявки на удаление и слияние.

## Пользователи (lib/accounts.ts)

`accounts.json`, версия формата 1: `id, name, login, passwordHash (scrypt), role,
personId, active, sessionVersion, createdAt, createdBy, updatedAt`.
`auth-log.jsonl` — журнал входов (успешные, неверный пароль, блокировки, смены паролей).

## Роли и права

| Действие | смотрит | дописывает | хранитель | владелец |
|---|:-:|:-:|:-:|:-:|
| Видеть древо, родство, перепись | ✓ | ✓ | ✓ | ✓ |
| Отметить свою карточку «Это я» | ✓ | ✓ | ✓ | ✓ |
| Добавлять и править людей и связи | | ✓ | ✓ | ✓ |
| Предложить удаление человека | | ✓ | ✓ | |
| Отвязать связь | | | ✓ | ✓ |
| Журнал изменений, восстановление удалённых | | | ✓ | ✓ |
| Подтверждать/отклонять заявки (не свои) | | | ✓ | ✓ |
| Слить дубли | | | заявкой | сразу |
| Удалить человека | | | заявкой | сразу |
| Заводить аккаунты, менять роли, закрывать вход, пароли | | | | ✓ |
| Скачивать копии, видеть журнал входов | | | | ✓ |

- Владелец один. Его создаёт команда на сервере (`scripts/create-owner.mjs`), а при переходе
  со старой версии — самый ранний хранитель становится владельцем автоматически.
- Регистрации нет: аккаунты заводит только владелец («Жители и доступ»).

## Вход и сессии

- Подписанная cookie (HMAC, `AUTH_SECRET`) на 30 дней: `{ id, sessionVersion, exp }`.
  Имя и роль читаются из `accounts.json` при каждом запросе — смена роли действует сразу.
- Без `AUTH_SECRET` (от 16 символов) сайт не запускается.
- «Выйти на всех устройствах», смена пароля и закрытие входа увеличивают `sessionVersion` —
  все старые сессии гаснут.
- 5 неверных паролей подряд — пауза 15 минут для этого логина.

## Заявки на подтверждение (lib/requests.ts)

1. Дописывающий или хранитель нажимает «Предложить удаление» (с причиной); хранитель на
   странице дублей нажимает «Слить». Создаётся `ChangeRequest` со снимком человека.
2. На карточке видна плашка «ждёт подтверждения», в меню хранителя — счётчик.
3. «Подтверждения» (`/admin/requests`): подтвердить может владелец или хранитель, но не автор
   заявки. Подтверждение выполняет действие; ошибка → статус `failed` с причиной.
4. Владелец удаляет и сливает сразу — это тоже пишется в журнал.

**Восстановление:** в журнале у записи «Удалён человек» есть «Восстановить» — человек
возвращается с тем же id, другими именами и связями с теми, кто ещё есть в древе
(`restorePerson`).

## Журнал (`/admin/log`)

Фильтры: по человеку (`?person=`), автору (`?actor=`), виду действия. На карточке у хранителя —
ссылка «История изменений». Для правок показывается «было → стало» по каждому полю.

## Резервные копии

| | Древо | Аккаунты |
|---|---|---|
| Как | `VACUUM INTO` (снимок на работающей базе) + `PRAGMA integrity_check` | копия `accounts.json` и `auth-log.jsonl` |
| Когда | каждые 6 ч (`TREE_BACKUP_HOURS`) и перед каждым запуском | раз в сутки |
| Хранится локально | 8 последних + 14 дневных + 8 недельных + 12 месячных | 3 последних + 14 дневных |
| В облако | зашифрованная (`.enc`) | зашифрованная (`.enc`) |

- Облако: `OFFSITE_REMOTE` + настройки rclone `RCLONE_CONFIG_OFFSITE_*` (S3: Yandex Object
  Storage, Selectel и др.). Срок хранения в облаке задаётся правилом жизненного цикла бакета.
- Шифрование: AES-256-GCM, ключ из `BACKUP_ENCRYPTION_KEY`. **Без ключа копии не расшифровать —
  храните его вне сервера.** Без ключа в облако ничего не отправляется.
- Состояние последней копии — `backups/status.json`, видно владельцу в «Жители и доступ».
- Владелец может в любой момент скачать свежую копию древа и аккаунтов там же.

### Восстановить древо

```sh
docker compose stop web
docker compose run --rm --no-deps web node scripts/restore-tree.mjs /backups/tree/tree-<дата>.db
docker compose start web
```
Текущая база не удаляется — сохраняется как `tree.db.replaced-<дата>`.

Из облака: скачать `.enc`, затем
`BACKUP_ENCRYPTION_KEY=... node scripts/decrypt-backup.mjs tree-<дата>.db.enc` и восстановить.

### Восстановить аккаунты

Остановить `web`, положить нужный `backups/accounts/accounts-<дата>.json` как
`data/accounts/accounts.json`, запустить.

## Запуск и обновление

**Первый запуск на новом сервере**
```sh
cp .env.example .env            # заполнить AUTH_SECRET (openssl rand -base64 48)
docker compose up -d --build
docker compose exec web node scripts/create-owner.mjs
```

**Переход со старой версии (одна база data/family-tree.db)** — ничего делать вручную не нужно:
при запуске контейнер сделает копию, перенесёт базу в `data/tree/tree.db` (старый файл
останется как `family-tree.db.before-split-<дата>`), пользователей — в `data/accounts`,
самый ранний хранитель станет владельцем. Нужно только задать `AUTH_SECRET` в `.env`
(все войдут заново).

**Обновление**
```sh
git pull
docker compose up -d --build
docker compose logs web | head -30   # копия перед запуском и db push прошли?
```
Если `prisma db push` сообщил о потере данных — сайт не запустится, данные не тронуты.
Такое изменение схемы нужно делать отдельно (миграцией с переносом данных).

**Проверять раз в месяц:** в «Жители и доступ» свежая дата копии и «Копия в облаке»;
раз в квартал — восстановить копию на отдельной машине и открыть.

## Безопасность

- Сайт открывать по HTTPS (Caddy или nginx перед контейнером) и включить
  `AUTH_COOKIE_SECURE="true"`.
- `.env`, `data/`, `backups/` не попадают в git и в образ.
- Копия аккаунтов содержит хеши паролей — храните как ключи.
